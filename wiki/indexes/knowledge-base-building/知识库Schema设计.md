# 知识库Schema设计

这页只回答一个问题：**怎样把“知识库建设方法”变成 AI 真正会持续遵守的结构约束。**

## 为什么需要 schema

当知识库还小的时候，你可以靠口头说明告诉 AI：

- 原始资料放哪
- 来源卡怎么写
- 输出结果怎么回流
- 哪些页面是入口，哪些页面只是原始来源

但只要来源开始变多、主题开始并行、工作流开始重复，口头说明就不够了。没有 schema，AI 每次都要重新猜：

- 目录边界
- 页面职责
- frontmatter 字段
- 命名方式
- 摄取、提问、回流、健康检查的顺序

schema 的作用，就是把这些“不能每次重猜”的规则固定下来。

## schema 在这套知识库里的位置

结合 [[2026-04-05-LLM-Wiki-持久化知识库模式]] 的三层结构，可以把当前库理解成：

- `raw/`
  事实来源层，只存原始资料和最小元数据
- `wiki/`
  结构化知识层，由 AI 编译和维护
- `schema`
  行为约束层，负责告诉 AI 应该如何处理 `raw`、如何维护 `wiki`、何时把结果写回 `outputs/`

在你当前的库里，schema 还不是单一文件，而是一个组合体：

- 顶层协作约束：系统级和会话级 `AGENTS.md`
- 仓库首页与入口页：[[README]]
- 方法页组：[[知识库建设方法总索引]]、[[知识库建设方法]]、[[知识库建设方法阅读地图]]
- 执行规范：[[2026-04-04-知识库构建执行指引]]
- 共享工作台与工作流页：[[知识库工作台]]、[[知识库健康检查清单]]、[[知识库+Codex-时间序列模型开发工作流]] 等

这页的目标，是把这组分散规则收束成一个更明确的 schema 设计视角。

## 一个有效 schema 至少要约束 4 件事

### 1. 结构约束

- `raw/`、`wiki/`、`outputs/`、`prompts/`、`assets/` 的职责边界
- `wiki/sources/`、`wiki/indexes/`、`wiki/concepts/` 的页面分工
- 哪些内容属于 `knowledge-base` 主题，哪些内容属于 `shared` 工作台

### 2. 页面约束

- frontmatter 字段最小集合
- 命名约定
- 页面标题与页面角色的对应关系
- 什么页面可以写长总结，什么页面只做原始保留

### 3. 操作约束

- 新来源如何 ingest
- 何时先写来源卡，何时更新索引，何时补概念页
- 查询结果何时写入 `outputs/`
- 高价值结论如何回流

### 4. 质量约束

- 健康检查频率
- 断链、孤页、缺摘要来源、重复概念如何处理
- 哪些变更需要同步更新入口页

## 当前这个库最值得写进 schema 的规则

如果后面要把 schema 落成仓库级 `AGENTS.md`，我建议优先固定这些内容：

1. `raw/` 是唯一摄取入口
2. 先有 `wiki/sources/`，再有 `wiki/indexes/`，最后才有 `wiki/concepts/`
3. `outputs/` 不是垃圾箱，只收高价值结果
4. 主题页优先互链，不做孤页
5. `knowledge-base` 主题页负责方法总纲与结构约束，`shared` 页面负责跨主题工作台与任务工作流
6. 原始网页统一使用稳定 frontmatter
7. AI 修改前先读上下文页，不凭空猜目录结构

## 适合写进未来 repo 级 AGENTS.md 的最小骨架

如果你后面要把 schema 从知识页再收束成仓库级 `AGENTS.md`，建议最小骨架是：

1. 仓库目标
2. 目录职责
3. 原始文档字段规范
4. 页面生成顺序
5. 输出与回流规则
6. 健康检查规则
7. 命名与互链规则
8. 对 AI 的默认行为要求

也就是说，`AGENTS.md` 负责“硬约束”，而知识页负责“解释这些约束为什么存在”。

## 怎么让 AI 真正用上 schema

不要只把 schema 文件放在那里。更稳的做法是：

1. 在首页保留稳定入口
2. 在 `knowledge-base` 主题入口里保留方法页组，在 `shared` 工作台里保留操作工作流
3. 在实际发任务时，显式给 AI 2 到 4 个入口页
4. 对复杂任务，优先同时给：
   - [[知识库建设方法]]
   - [[知识库Schema设计]]
   - 相关主题总索引
   - 相关来源卡

如果不给入口，AI 往往会退化成“只看眼前文件、临时猜规则”的模式。

## 什么时候更新 schema

以下情况都值得更新一次 schema，而不是只改单页内容：

- 新增了一类原始来源
- 新增了一类输出格式
- 新增了一个稳定工作流
- 反复出现同类结构错误
- 你发现 AI 总在同一个边界上做错

判断标准很简单：

如果一个规则你已经说了两次以上，它就不该继续只存在于对话里。

## 一个直接可用的实践建议

短期内，不必急着再新建一个仓库级 `AGENTS.md`。更稳的顺序是：

1. 先把 `knowledge-base` 主题页补齐
2. 观察 AI 在真实任务里最常犯的结构错误
3. 再把那些“高频、稳定、不可协商”的规则抽到 repo 级 `AGENTS.md`

这样 schema 会是从真实使用中长出来的，而不是一开始就写成一份过度设计的规范。
