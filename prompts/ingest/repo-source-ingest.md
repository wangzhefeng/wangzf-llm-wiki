请基于我提供的代码仓库地址、所属专题和当前知识库上下文，直接执行一次“仓库来源沉淀”。

适用场景：
- GitHub 仓库
- 算法实现仓库
- 实验框架
- 工程化预测系统

执行约束：
- 当前知识库采用 `raw -> wiki/sources -> wiki/indexes -> wiki/concepts -> outputs` 分层
- `raw/` 是唯一摄取入口
- 仓库原始材料统一先进入 `raw/repos/`
- 不要把整个仓库粗暴地当成一条来源卡
- 优先把仓库拆成若干“知识单元”，例如：
  - 方法策略
  - 特征工程
  - 训练流程
  - 评估流程
  - 预测流程
  - 工程组织
- 先补来源层，再补索引层，最后补概念层
- 不要编造 README、代码、配置、脚本中没有出现的信息
- 如果仓库信息不足以支撑概念提升，要明确写出 `missing_context`

请按下面顺序执行：

1. 在 `raw/repos/` 创建或更新 1 页仓库入口笔记
   - 文件名建议：`repo-组织名-仓库名.md`
   - 至少记录：
     - `source_type: repo`
     - `source_url`
     - `created_at`
     - `topics`
     - `related_concepts`
     - `status`
   - 页面正文至少包括：
     - 仓库用途
     - 关键入口文件
     - 关键目录
     - 训练、测试、预测涉及的脚本或模块
     - 建议拆分的知识单元

2. 在 `wiki/sources/<topic>/` 中为仓库创建来源卡
   - 如果仓库内容较薄，可以只建 1 张总来源卡
   - 如果仓库内容较厚，优先按知识单元拆成多张来源卡
   - 每张来源卡必须保留：
     - `source_type`
     - `source_url`
     - `source_path`
     - `created_at`
     - `topics`
     - `related_concepts`
     - `status`
   - 每张来源卡正文至少包括：
     - 这个知识单元讲什么
     - 核心做法
     - 输入 / 输出
     - 关键模块、脚本、配置
     - 适用场景
     - 局限与代价

3. 只在确有增量时更新 `wiki/indexes/<topic>/` 和 `wiki/concepts/<topic>/`
   - 优先回写：
     - 总索引
     - 阅读地图
     - 与仓库最相关的 1-3 个概念页
   - 如果仓库沉淀出了新的稳定知识单元，可以新增概念页
   - 不要把 README 原文直接搬进概念页

4. 如果仓库里有重要架构图、流程图或实验图
   - 复制到 `raw/assets/attachments/<topic-slug>/<repo-slug>/`
   - 新建的 `wiki/` 页面只引用复制后的本地路径

5. 最后做最小验证
   - 检查 `raw/repos/` 仓库入口页是否已创建
   - 检查来源卡是否已创建并带关键 frontmatter
   - 检查索引页和概念页是否已补入口或互链
   - 检查新增链接是否能解析
   - 检查有没有只写标题、没有信息量的占位页

输出要求：
- 不要只给计划，直接实施
- 最终汇报按三部分组织：
  - 做了什么
  - 怎么验证
  - 剩余风险
- 如果你判断这个仓库目前只值得沉淀到来源层，要明确说明原因
- 如果仓库内容适合产出方法对比、工程流程总结或阅读地图，可在最后给出 `outputs/` 建议

使用时我会补充这些最小信息：
- 仓库 URL
- 所属专题，例如 `timeseries`
- 希望优先连接的概念页（可选）
