# LLM wiki 核心能力缺口与补齐路线

## 这份综述回答什么问题

它不再重复解释“为什么要建这个知识库”，而是收束一个更实际的问题：**当前这套 LLM wiki，已经具备哪些核心能力，还缺哪几块最关键的工作流。**

## 已经具备的能力

当前库已经稳定具备这些基础层能力：

- `raw -> wiki -> outputs` 三层目录已经跑通
- `sources / indexes / concepts` 的页面分工已明确
- `web` 和 `repo` 两类来源已有稳定 intake prompt
- shared 工作台、维护检查和输出工作流已经有明确入口
- `answers + slides + figures` 已有真实样例

换句话说，这个库已经不只是“有很多 Markdown 文件”，而是已经有一条可运行的最小知识编译链。

## 此前最真实的 5 个缺口

### 1. `query` 只有方法，没有独立入口

方法页已经明确把 `query` 视为核心操作，但此前没有独立 prompt，也没有单独的共享工作流页。结果是：能问，但不稳定；能做，但不制度化。

### 2. `log` 只存在于设计层，没有时间导航落点

库里已经区分了内容导航和时间导航，但此前没有稳定的日志落点，也没有操作记录索引。上一轮做了什么，很容易重新回到对话里找。

### 3. 问题地图缺位

当前主题总索引和阅读地图已经存在，但“现在该问什么”没有共享入口。对 LLM wiki 来说，这会直接削弱 query 的起点质量。

### 4. intake 模板覆盖面不够

当前 intake 模板主要覆盖了 `web` 和 `repo`。对一个已经明确支持 `paper / dataset / image / local_note` 的知识库来说，这意味着来源类型和工作流类型还没有完全对齐。

### 5. `syntheses/` 还是空目录

单次结果和演示稿已经有样例，但阶段性综述还没有真正产出。缺这层时，知识库会更像“很多单条结果”，而不是“会逐步收束的研究工作域”。

## 本轮补齐了什么

本轮已经把上面 5 个缺口补成了可直接复用的 Markdown 结构：

- `query`
  已新增 [[知识库问答与研究工作流]] 与 [[prompts/query/knowledge-base-query]]
- `log`
  已新增 [[知识库操作记录索引]]、[[prompts/logging/operation-log]] 与 `outputs/logs/`
- 问题地图
  已新增 [[知识库问题地图]]
- intake 覆盖
  已补 `paper / dataset / image / local_note` 四类 intake prompt
- synthesis
  已新增当前这份综述，作为 `outputs/syntheses/` 的首个样例

## 这轮补齐后的结构变化

现在这套库的最小工作链已经更接近：

`ingest -> sources -> indexes/concepts -> query -> outputs -> backfill -> log -> lint`

这比之前多出来的，不只是几个页面，而是三类以前缺位的结构角色：

- 问题入口
- 时间导航
- 阶段性收束

## 仍然没必要现在就做的事

这轮补齐后，依然不建议马上去做：

- 向量库或复杂 RAG
- 重型数据库
- 自动化汇总脚本
- 大规模页面重构

因为当前阶段最重要的，仍然是先让这条 Markdown 工作链在真实任务里反复跑顺。

## 建议的下一步

1. 在 `timeseries` 主题补第一张专题问题地图
2. 用新的 query 工作流跑一轮真实研究问题，验证 answer / synthesis / log 的回流闭环
3. 下一轮健康检查时，把 `log` 和 `syntheses` 纳入检查范围
