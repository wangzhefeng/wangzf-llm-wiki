# LLM wiki 构建流程总结

## 文档目标

这份总结不回顾知识库主题内容，而是基于 `raw/codex_threads/` 中的历史线程，收束“如何从空仓库或低结构仓库建立一套可持续运行的 LLM wiki 工作域”。

主证据线程：

- `2026-04-07-知识库搭建与工作流固化线程.md`
- `2026-04-07-llm-wiki-工作流补齐与-schema-固化线程总结.md`
- `2026-04-07-知识库建设方法主题落地与迁移线程总结.md`
- `2026-04-07-知识库方法页组重构与工作台收口线程总结.md`

## 适用场景

- 从普通仓库升级为可被 AI 持续使用的 Markdown 知识库
- 将本地历史文档、网页、仓库等资料纳入统一工作链
- 已有知识页开始增多，页面角色和目录边界变得混乱
- 需要把“知识库建设方法”从零散文档整理为稳定主题和规则页

## 流程总览

构建流程的核心不是先写很多内容，而是先建立一条稳定的知识编译链：

`raw -> wiki/sources -> wiki/indexes -> wiki/concepts -> outputs`

在这条链之外，再补三类支撑层：

- 入口层：`README.md`、工作台、总索引、阅读地图
- 规范层：frontmatter、来源类型、Schema、repo 级约束
- 复用层：prompt 模板、工作流页、样例产物

## 标准步骤

### 1. 先固定仓库骨架与页面分层

- 建立 `raw/`、`wiki/`、`outputs/`、`prompts/`、`raw/assets/` 基本结构
- 在 `wiki/` 内明确 `sources / indexes / concepts` 三类页面角色
- 先接受“第一次结构设计不会完美”，后续允许在真实专题进入后重构

这一阶段最重要的经验是：先有工作域，再谈内容规模。没有稳定目录边界，后续所有主题都会继续堆在根目录或平铺失控。

### 2. 先把原始资料归到 `raw`，不要直接跳过来源层

- 本地历史文档进入 `raw/notes/`
- 网页进入 `raw/web/`
- 仓库进入 `raw/repos/`
- 其它类型按 `paper / dataset / image / notes` 归档

线程证据反复指向同一个判断：直接从原始资料跳到概念页，会让知识库失去来源可追溯性，也不利于后续 AI 继续编译。

### 3. 先建来源卡，再建索引和概念页

- 第一层产物是 `wiki/sources/`，回答“这份材料讲了什么、价值是什么、连到哪些概念”
- 第二层产物是 `wiki/indexes/`，回答“这个主题从哪里进入、按什么路径阅读”
- 第三层产物是 `wiki/concepts/`，回答“沉淀出了哪些稳定概念和方法”

这是几条构建线程里最稳定的规则之一，也是后续维护流程反复坚持的口径。

### 4. 让“主题层”和“工作台层”分开生长

- `knowledge-base/` 这类主题目录负责回答“为什么这样建、方法是什么、Schema 是什么”
- `shared/` 负责回答“现在要怎么做、从哪里进入、维护入口在哪里”
- 阅读地图、总索引、Schema 页、工作台页不能混成一个大杂烩

这一点在“方法页组重构与工作台收口”“健康检查与结构分层重构”两条线程中都被反复验证。真正难的不是补内容，而是把页面职责分清。

### 5. 用真实专题和真实来源跑通首轮闭环

- 用本地专题文档验证 `notes -> sources -> indexes/concepts`
- 用网页来源验证 `web-source-intake`
- 用仓库来源验证 `repo-source-intake`
- 至少产出一份 `outputs/answers/` 或 `outputs/slides/`，证明知识库不是静态笔记堆

线程里用 `operations-research`、`timeseries`、scikit-learn 页面、`tsproj_ml` 仓库跑通了首轮闭环。构建流程只有经过真实来源验证，后续规则页才有可信度。

### 6. 在结构逐渐稳定后，再补规则页和 repo 级约束

- 先形成方法页、执行指引、Schema 设计、工作台入口
- 再根据真实使用中暴露的稳定规则，决定是否上收为 `AGENTS.md`、`CLAUDE.md`
- 不在一开始就假定所有规则都该进入 repo 级硬约束

这一步的关键经验是：规则应从真实工作流中长出来，而不是提前凭空设计一整套抽象。

## 输入与输出

输入通常包括：

- 原始文档、本地历史笔记、网页、仓库、数据集等资料
- 用户给出的主题边界、入口文件、迁移要求
- 现有方法页、执行指引、README、工作台等上下文

构建流程的典型输出包括：

- `raw/` 中标准化的原始来源
- `wiki/sources/` 来源卡
- `wiki/indexes/` 总索引、阅读地图、问题入口、工作台入口
- `wiki/concepts/` 概念页
- `prompts/` 中可复用 intake / query / lint 模板
- `outputs/` 中真实样例产物

## 角色分工

用户负责：

- 给出主题边界、优先级、删除与迁移约束
- 在 provenance 判断、页面角色边界、入口取舍上做关键纠偏
- 决定何时把经验从页面层上收到 repo 级约束层

AI 负责：

- 先读现有结构，再判断是内容缺口还是工作流缺口
- 按 `raw -> sources -> indexes -> concepts` 顺序落地
- 在改结构前先判断页面组角色，而不是围绕单页盲改
- 每轮收尾明确“做了什么、怎么验证、还有什么未固化”

## 常见失败点与反模式

- 直接把原始来源写成概念页，跳过来源层
- 看到新文件存在就认为迁移已完整，没有做覆盖率核查
- 把“知识库建设方法”主题和 `shared` 工作台混在一起，页面角色失焦
- 为了图谱好看给不该联网的页面强行补链接
- 在结构还没跑顺之前就急着做脚本、自动化、RAG 或复杂数据库
- 只改正文，不同步首页、工作台、阅读地图和旧入口

## 从线程证据抽出的关键经验

- 构建流程最先要固定的是“层级”和“角色”，不是内容数量
- 主题一旦增多，目录结构必然演化，第一次设计通常只是最小可用版
- 删除旧文件前必须先做覆盖率核查和残留引用审计
- 方法页组重构应先判定 provenance 和页面角色，再小步补丁式推进
- prompt、工作流页、样例产物、回链入口这四件套一起补，比只补单页更稳

## 仍未固化的问题

- 现有方法页与 Schema 页虽然已较清楚，但还没有直接抽象成正式 skill
- 不同来源类型的 intake 规则已补齐，但是否长期稳定仍需更多真实任务验证
- 页面组重构、原始文档迁移、入口收口等动作还缺统一的检查清单模板
