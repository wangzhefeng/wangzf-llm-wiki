# 个人知识库诞生设想

## 文档定位

这份文档是当前知识库的诞生文档，也是我对 [[2026-04-05-Karpathy最新硬核分享：用大模型和Obsidian打造个人本地知识库]] 所代表模式的本地化吸收版本。它回答的是“为什么这样建库、边界在哪里、长期如何演化”，作为当前库的原则层总纲；更具体的执行细节放在 [[2026-04-04-知识库构建执行指引]]。

## 来源关系

- 外部启发来源：[[2026-04-05-Karpathy最新硬核分享：用大模型和Obsidian打造个人本地知识库]]
- 内部吸收结果：当前这份“个人知识库诞生设想”
- 处理原则：不照抄外部案例，而是把其中适合当前仓库的结构判断、角色分工和长期方向内化为自己的原则稿

## 这页与其他页面的分工

- 这页负责原则层，解释为什么采用 `raw -> wiki -> outputs` 的建库方式
- [[2026-04-04-知识库构建执行指引]] 负责执行层，解释目录、字段、顺序和日常操作
- [[知识库建设方法]] 负责归纳层，把原则层与执行层收束成统一入口

## 核心判断

- 个人知识库不应只是一个“更好看的笔记本”，而应是一个由 LLM 驱动的持续工作域。
- 外部资料应统一先进入 `raw/`，再由 LLM 逐步编译成 `wiki/`，而不是一开始就人工改写成总结。
- wiki 层优先用普通 Markdown、摘要、索引、反链和概念页来组织知识，不急着引入复杂 RAG。
- Obsidian 负责做前端和浏览界面，LLM 与 CLI 工具负责阅读、整理、提问、输出和持续维护。
- 高价值输出不应停留在临时对话中，而应写回 `outputs/` 或继续回流到 `wiki/`。

## 标准工作链

`摄取 -> 来源摘要 -> 主题索引/阅读地图 -> 概念页 -> 问答/研究 -> 输出 -> 回流 -> 健康检查`

这条链路的重点不是“一次写完”，而是每轮都能继续向前编译。

## 数据摄取

- 源文档包括网页、论文、代码仓库、数据集、图片等，都应先进入 `raw/`。
- 网页正文适合通过 `Obsidian Web Clipper` 直接保存为 Markdown。
- 与网页相关的关键图片、截图和图表，最好也一并本地化，方便 LLM 在后续输出中直接引用。
- 摄取阶段的目标是先保留来源，而不是立刻写成长篇总结。

## Obsidian 的角色

- Obsidian 不是知识生成引擎，而是这套系统的前端与工作台。
- 它负责展示 `raw/`、`wiki/`、`outputs/` 和本地附件，让知识可以被浏览、跳转和复查。
- 反链、出链、图谱和附件视图，能帮助人和 LLM 共同发现这个库是否真的长成了网络结构。

## 人与 LLM 的分工

- 人负责：定主题、挑材料、纠偏、做价值判断、决定下一轮问题。
- LLM 负责：读原文、写摘要、补索引、组织概念、生成输出、做健康检查。
- 工具层负责：把网页、仓库、图片、结果页和本地资料稳定地落成 Markdown 与附件。

## 围绕 wiki 的问答与研究

- 当 wiki 积累到一定规模后，LLM 可以不依赖复杂 RAG，也能围绕现有摘要、索引和概念页完成较复杂的问题展开。
- 中小型个人研究库的关键，不一定是检索技术，而是索引是否稳定、来源是否有摘要、概念之间是否有互链。
- 问题的价值不在于“让 LLM 聊天”，而在于让它围绕已有知识网络做进一步研究、对照和判断。

## 输出形态

- 输出不应停留在终端文本里，而应优先变成 Markdown 文件、演示稿、图表或其他可归档结果。
- 不同问题可以对应不同输出形式，例如：
  - `outputs/answers/`：单次问答结果
  - `outputs/slides/`：Marp 演示稿
  - `outputs/figures/`：图表、流程图、示意图
- 输出完成后应尽量回流到 `wiki/`，成为后续研究的上下文，而不是一次性消费品。

## 健康检查与维护

- 知识库不是“收进去就结束”，而需要持续健康检查。
- 检查重点包括：数据不一致、缺失信息、可补充来源、值得新建的候选条目、结构失衡和断链。
- 健康检查的目标不是追求整洁本身，而是让这个库继续可问、可扩、可维护。

## 辅助工具与自动化

- 随着库体量增长，简单的搜索工具、检查脚本、图表脚本或命令行辅助工具会自然出现。
- 这些工具的价值，不是替代知识结构本身，而是帮助 LLM 更快读库、检查库、扩充库。
- 比起一开始就搭重型系统，先让目录、字段、索引、回流方式稳定下来更重要。

## 为什么采用 Obsidian + Markdown

- Markdown 文件天然适合 LLM 读取、改写和版本化管理。
- Obsidian 能把 `raw/`、`wiki/`、`outputs/` 和附件统一呈现为一个可浏览的工作台。
- 反链、出链、图谱和附件管理，能直接暴露知识库是否真的长成网络。

## 长期演化方向

- 随着知识库变大，健康检查、缺口补全、候选条目发现会成为日常维护动作。
- 小型搜索工具、仓库检查脚本、可视化脚本会逐步变成 LLM 的辅助 CLI 工具。
- 再往后，才值得讨论向量检索、合成数据或微调，把知识进一步沉淀到模型能力中。
- 更远一点看，临时 wiki、自动清理、多轮归纳和最终报告生成，可以视为同一条方法链的延伸，而不只是“写几篇笔记”。
