# 知识库构建执行指引

## 文档定位

## 方法论总览

这套方法不是“做一个更花哨的笔记软件”，而是把个人知识库拆成一条由 LLM 驱动的工作链：

`摄取 -> 编译 wiki -> 问答/研究 -> 输出 -> 归档回流 -> lint/质检`

这条链路里最重要的判断有三个：

1. `raw/` 是唯一摄取入口。所有外部材料先进入 `raw/`，不要一开始就手工改写成“自己的总结”。
2. wiki 层优先用普通 Markdown 和互链，不急着上向量库或复杂 RAG。对个人中小型知识库，摘要、索引、反链已经足够强。
3. LLM 主要负责写和维护 wiki；人主要负责定主题、挑资料、纠偏、提出下一轮问题。

这套方法的目标，不是让每条笔记都变成“最终答案”，而是让知识库逐步变成 LLM 可持续工作的工作域。

## 这套执行法新增固定的 4 个结构判断

### 1. 三层结构要分清

- `raw`
  原始来源层，只读，不作为最终结论页
- `wiki`
  结构化知识层，由 LLM 负责维护来源卡、索引页、概念页与互链
- `schema`
  行为约束层，告诉 AI 目录职责、页面规范、操作顺序和回流规则

### 2. 三类核心操作要固定

- `ingest`
  处理新来源，把原始资料转成来源卡并更新索引
- `query`
  围绕现有 wiki 做研究、问答、比较、输出
- `lint`
  对 wiki 做健康检查，修复矛盾、断链、孤页和缺口

### 3. 内容导航与时间导航要分开

- `index`
  内容导向，回答“当前主题里有什么、先看什么、它们怎么相连”
- `log`
  时间导向，回答“最近摄取了什么、回答过什么、做过哪些检查”

在当前库里，`index` 的角色主要由主题总索引、阅读地图和 shared 工作台承担；`log` 可以先由阶段性操作记录页承担，等工作流稳定后再决定是否收束成统一文件。

### 4. CLI 工具是增强层，不是前提

- 搜索、批量检查、图表和转换脚本都可以逐步补
- 它们服务于 `raw/wiki/schema` 结构，而不是替代结构本身
- 在来源量和页面量还不大时，优先把索引、摘要和互链做稳定

## 适用范围

- 有持续积累价值的研究主题
- 来源混合，包含网页、论文、仓库、数据集、图片、本地历史资料
- 希望 LLM 长期参与整理、检索、归纳和输出，而不是只做一次性问答

更适合下面几类场景：

- 某个研究主题会持续积累几周到几个月，而不是一次性读完就结束
- 你更在意“以后还能继续问、继续扩展”，而不是一次性整理成一篇文章
- 你愿意把大量一线整理工作交给 LLM，而不是自己手工维护大量卡片笔记

不太适合的场景：

- 只是做很轻量的收藏夹
- 资料量极小，且不会持续扩张
- 你希望每一页笔记都由自己逐字编写

## 起步前的最小工具准备

先按轻量方案起步，只准备这几项：

- `Obsidian`
  作为知识库前端，用来看 `raw/`、wiki 和输出结果
- `Obsidian Web Clipper`
  用来把网页正文直接保存到 vault
- 一个可稳定生成 Markdown 的 LLM
  重点是能读多文件上下文、能输出结构化 Markdown、能按提示词持续改写
- 可选：`Marp`
  当你希望把专题输出成演示稿时再加

建议在 Obsidian 里提前打开这些设置：

- `Files & Links -> Automatically update internal links`
- `Files & Links -> Default location for new attachments`
- `Use [[Wikilinks]]`
- `Backlinks` 核心插件
- `Outgoing links` 核心插件

这些设置的目的很简单：

- 自动更新内部链接，降低重命名时的维护成本
- 固定附件目录，让图片、本地 PDF、截图长期可引用
- 反链和出链视图，帮助你判断 wiki 是否真的长成网络，而不是一堆孤立笔记

## 标准目录结构

```text
your-vault/
├── raw/
│   ├── web/
│   ├── papers/
│   ├── repos/
│   ├── datasets/
│   ├── images/
│   └── local-notes/
├── wiki/
│   ├── sources/
│   ├── indexes/
│   └── concepts/
├── outputs/
│   ├── answers/
│   ├── syntheses/
│   ├── slides/
│   └── figures/
├── prompts/
└── raw/assets/
```

每层的职责固定下来：

- `raw/`
  外部来源原件，只做收集、落盘、最小元数据记录，不做人写总结
- `wiki/sources/`
  每个来源的一页摘要卡，负责“这份资料讲了什么、重要性是什么、连到哪些概念”
- `wiki/indexes/`
  主题索引、来源索引、阅读地图、问题地图
- `wiki/concepts/`
  概念条目、人物条目、方法条目、工具条目
- `outputs/`
  问答结果、专题综述、幻灯片、图表
- `prompts/`
  常用提示词模板，避免每次都从头写
- `raw/assets/`
  通用图像、封面图、引用素材、非来源型附件
- `schema`
  在当前仓库里不一定单独成目录，它更多体现为 `AGENTS.md`、方法页、工作流页和提示词模板的组合约束

推荐命名约定：

- 原始网页：`YYYY-MM-DD-标题.md`
- 论文笔记：`YYYY-作者简写-标题短名.md`
- 仓库来源：`repo-组织名-仓库名.md`
- 概念条目：`概念名.md`
- 输出结果：`YYYY-MM-DD-主题-用途.md`

## index、log 与 schema 在当前库里的落点

- `schema`
  先由 `AGENTS.md`、[[知识库建设方法]]、[[知识库Schema设计]] 和各类工作流页共同承担
- `index`
  优先落在 `wiki/indexes/`，包括主题总索引、阅读地图、问题入口和 shared 工作台
- `log`
  可以先按主题或任务保留阶段性操作记录；只有当 ingest、query、lint 足够频繁时，再收束成统一日志页

这里的重点不是先补齐一个“完美目录”，而是先让这三种角色在库里稳定存在。

## 标准页面生成顺序

1. 先把原始资料纳入 `raw/`
2. 再生成 `wiki/sources/` 来源卡
3. 再建立 `wiki/indexes/` 总索引、阅读地图和问题入口
4. 最后沉淀 `wiki/concepts/` 概念页

不要跳过来源层直接写概念百科。

## 原始文档的标准字段

建议原始网页或原始 Markdown 至少保留这组 frontmatter：

```yaml
---
source_type: web
source_url: https://example.com/article
title: 示例文章标题
author: 作者名
published_at: 2026-04-04
created_at: 2026-04-05
topics:
  - 知识库维护
related_concepts:
  - 知识库建设方法
status: inbox
---
```

字段说明：

- `source_type`
  来源类型，建议固定为 `web`、`paper`、`repo`、`dataset`、`image`、`local_note`
- `source_url`
  外部来源链接；本地文档可省略
- `title`
  原文标题
- `author`
  作者、机构或公众号名
- `published_at`
  原文发布日期；未知时可留空
- `created_at`
  进入知识库的日期
- `topics`
  所属主题标签，控制在 1 到 3 个
- `related_concepts`
  已知相关概念，用于后续 wiki 归纳
- `status`
  建议使用 `inbox`、`summarized`、`linked`、`archived`

概念页建议保留：

```yaml
---
created_at: 2026-04-04
topics:
  - llm-knowledge-base
related_concepts:
  - 来源摘要
  - 反向链接
status: active
---
```

## 第一次起库的最小闭环

1. 先确定一个具体专题，不要一开始就整理“整个世界”
2. 先收 10 到 20 份关键资料进 `raw/`
3. 先补来源卡，再补索引页，再补概念页
4. 每做完一轮问答或研究，把高价值结果写回 `outputs/`
5. 开始下一轮前，先做健康检查

更细的首轮执行方式如下：

### 第 1 步：创建 vault 并配置基础设置

- 新建一个 Obsidian vault
- 创建 `raw/`、`wiki/`、`outputs/`、`prompts/`、`raw/assets/`
- 建议把默认附件目录固定到 `raw/assets/attachments/`

### 第 2 步：先选一个具体研究主题

不要上来就做“我的全部知识库”。先收缩成一个可管理主题，例如：

- `LLM 知识库`
- `时间序列预测`
- `控制算法`
- `个人健康数据分析`

第一轮建议只放 10 到 20 份资料，来源尽量混合：

- 5 到 8 篇网页文章
- 2 到 5 篇论文
- 1 到 3 个代码仓库
- 若干关键图片或图表

### 第 3 步：把原始资料摄取进 `raw/`

- 网页文章
  用 `Obsidian Web Clipper` 直接保存到 `raw/web/`
- 论文
  把 PDF 放到 `raw/papers/`，再补一页同名 Markdown 记录元数据和摘要任务
- 代码仓库
  先记录仓库主页、README、关键文档、关键目录说明到 `raw/repos/`
- 图片
  与主题强相关的架构图、流程图、实验结果图，直接存到 `raw/images/` 或附件目录

这里的原则是：

- 先“抓住来源”，再让 LLM 编译
- 不要一边摄取一边手工写长篇总结
- 重要图片尽量本地化，不只保留外链

### 第 4 步：为每个来源生成来源摘要页

每份来源摘要页建议包含：

1. 这份资料在讲什么
2. 3 到 7 条关键信息
3. 它和哪些概念相关
4. 它和库里其他哪些来源相关
5. 它还缺什么上下文

可复用提示词：

```md
请基于我提供的 raw 来源材料，生成一页 wiki/sources 来源摘要卡。

要求：
- 输出 Markdown
- 保留 frontmatter
- 给出 3-7 条关键结论
- 单独列出 related_concepts
- 单独列出 related_sources
- 如果材料有明显缺口，列出 missing_context
- 不要编造未出现的信息
```

### 第 5 步：再生成主题索引页

建议至少有两类索引：

- `主题总索引`
  当前主题下有哪些来源、概念、子问题
- `阅读地图`
  如果新读者要快速进入这个主题，应该先看什么，再看什么

### 第 6 步：最后生成概念条目页

每个概念页建议包含：

- 一句话定义
- 该概念在当前主题中的意义
- 关键来源
- 相关概念
- 已知争议或边界
- 还值得继续追问的问题

## AI 执行时的默认规则

- 先读 `schema`、相关索引页和来源卡，再决定怎么批量修改
- 先读 `raw/`，再写 `wiki/`
- 先补最近闭环，再扩张范围
- 不直接把原始来源改写成结论页
- 新专题先建立来源和入口，不急着过早抽象
- 所有稳定结论优先写进文件，而不是只留在对话中

## 三类核心操作：ingest、query、lint

### Ingest：摄取与编译

每次新增资料，先问自己两个问题：

1. 这份资料值不值得进入库，而不是只留在浏览器收藏夹里？
2. 它进入库后，会支持什么后续问题？

如果答案不明确，就不要急着收。建议把新增资料统一先放进 `status: inbox`，等一轮摘要生成后再升级状态。

完成摄取后，不要停在 `raw/`，而要继续完成一轮最小编译：

- 生成 `wiki/sources/` 来源摘要页
- 更新相关主题总索引和阅读地图
- 视情况补充概念页或候选概念
- 为本轮动作补一条操作记录，方便回看最近 ingest 了什么

### 编译 wiki

所谓“编译”，就是把 `raw/` 中的来源逐层转成结构更强的 wiki。

推荐编译顺序：

1. `raw/*` -> `wiki/sources/*`
2. `wiki/sources/*` -> `wiki/indexes/*`
3. `wiki/sources/* + wiki/indexes/*` -> `wiki/concepts/*`
4. 检查并补互链、反链入口、相关来源

对 LLM 的要求不是“一次写完”，而是分层做：

- 第一层只忠实抽取来源
- 第二层才开始归纳主题
- 第三层才开始抽象概念

### Query：提问、输出与回流

不要直接对 LLM 问大而空的问题，例如：

- “请总结这个主题”
- “这个领域未来会怎样”

更有效的方式是先让它做检索型准备，再做回答。

推荐三段式提问法：

1. 先列相关条目
2. 再列冲突、缺口、未覆盖证据
3. 最后基于现有库回答

可复用提示词：

```md
请只基于当前 wiki，先完成三件事：

1. 列出与“LLM 知识库”最相关的 sources、concepts、indexes
2. 标出其中互相冲突、定义不清或证据不足的点
3. 再回答问题：“对于个人研究者，这套方法最适合从哪里开始实践？”

输出要求：
- 先给证据路径，再给答案
- 答案引用涉及的条目名
- 最后给出 3 个值得继续追问的问题
```

Query 不只是“聊天提问”，而是围绕现有 wiki 进行一次可回收的研究动作。

### 输出

输出不要停留在终端，建议按用途分流：

- `outputs/answers/`
  单次问答结果
- `outputs/syntheses/`
  某一主题的阶段性综述
- `outputs/slides/`
  Marp 幻灯片
- `outputs/figures/`
  图表、示意图、流程图说明

### 归档回流

每次高价值输出完成后，至少做两件事：

1. 在相关概念页里增加“延伸阅读”或“相关输出”链接
2. 把这次问答中新出现的概念、争议、候选来源写回 `wiki/indexes/` 或 `wiki/concepts/`

如果不回流，知识库就只是在重复消耗上下文，不是在积累可复用资产。

同一轮 query 最好也补一条操作记录，至少说明问题、证据路径和回流结果。

## Lint：健康检查与持续增强

建议固定做 7 类检查：

1. 孤儿条目
   没有反链、没有出链、没有被索引引用的页
2. 死链
   重命名后未更新、附件路径失效、来源地址失效
3. 重复概念
   同一个概念被写成多个近义标题
4. 缺摘要来源
   `raw/` 里已摄取，但还没有 `wiki/sources/` 摘要页
5. 附件不完整
   关键图片或 PDF 只保留外链，没有落地到本地
6. 可扩展候选
   LLM 从现有 wiki 中挖出的新概念、新问题、新来源方向
7. 过时结论
   已被新来源修正，但旧索引或旧概念页仍保留原判断

可复用提示词：

```md
请把当前知识库当成一个 Markdown wiki，做一次健康检查。

重点检查：
- 孤儿条目
- 重复概念
- 定义冲突
- 已摄取但未摘要的 raw 来源
- 关键附件缺失
- 已经过时但仍未修正的结论
- 值得新建的概念页或索引页

输出格式：
- 问题清单
- 每个问题对应的证据路径
- 建议修复动作
- 最后给出优先级最高的 5 个下一步
```

每次 lint 的目标不是“整理得更整齐”，而是让库继续可问、可扩、可维护。

## 何时引入自动化

一开始不要急着写复杂脚本。只有在这些信号出现时，再加自动化：

- 同类来源已经稳定超过 30 到 50 份
- 你开始重复做同样的摘要、重命名、归档操作
- 你已经知道哪些字段、目录和输出格式是稳定的
- 你开始需要批量检查死链、状态字段、缺摘要来源

建议的自动化顺序：

1. 先固定目录和命名
2. 再固定提示词模板
3. 再补简单 CLI 或脚本
4. 最后才考虑更复杂的搜索、增量编译、数据库或向量检索

如果后续想做自动化增强，可以优先考虑：

- 批量生成来源摘要页
- 批量检查 frontmatter 缺失字段
- 批量发现孤儿条目和未链接概念
- 为 LLM 提供一个本地 CLI 搜索工具

## 常见坑与边界条件

### 坑 1：一开始就试图整理“人生全部知识”

结果通常是目录很大、内容很空、没有一条闭环跑通。更好的做法是先选一个具体主题，把第一轮 10 到 20 份资料完整跑完。

### 坑 2：过度手改 wiki

如果 wiki 主要靠手工维护，你很快会回到普通笔记系统的维护负担里。

建议原则：

- 人工主要改结构、边界、优先级
- LLM 主要改摘要、条目、互链、索引

### 坑 3：只保留来源链接，不落地附件

长期看，网页可能失效、图片可能消失、仓库可能重构。关键资料尽量保留本地副本，特别是：

- 核心图表
- 论文 PDF
- 重要截图
- 被频繁引用的网页正文

### 坑 4：概念页不做互链

没有互链，Obsidian 的反链和图谱优势就发挥不出来，LLM 也更难借结构快速读出关系。

### 坑 5：只做问答，不做回流

这样输出只是一次性消费品，不会增强知识库。

### 坑 6：太早引入 RAG 或复杂后端

在个人中小型研究库阶段，真正的瓶颈通常不是“检索能力不够”，而是：

- 来源没整理干净
- 摘要没写稳定
- 索引没建立起来
- 互链不够
- 问题不够具体

## 一个可直接照抄的起步清单

1. 安装 `Obsidian`
2. 安装 `Obsidian Web Clipper`
3. 新建一个 vault
4. 创建目录：`raw/`、`wiki/`、`outputs/`、`prompts/`、`raw/assets/`
5. 在 Obsidian 中启用 `wikilinks`、自动更新内部链接、固定附件目录
6. 选一个窄主题，只收 10 到 20 份资料
7. 把网页放进 `raw/web/`，论文放进 `raw/papers/`，仓库资料放进 `raw/repos/`
8. 为每份来源补最小 frontmatter
9. 让 LLM 先生成 `wiki/sources/` 来源摘要页
10. 让 LLM 再生成 `wiki/indexes/` 主题索引页和阅读地图
11. 再生成 `wiki/concepts/` 概念页
12. 围绕 wiki 提一个具体问题，输出到 `outputs/answers/`
13. 把高价值输出回链到相关概念页
14. 做一次 wiki lint，补死链、孤儿条目、缺摘要来源

## 起步心法

如果只保留一句话，这套方法的关键不是“把资料存下来”，而是：

先把来源稳定摄取进 `raw/`，再让 LLM 分层编译成可互链的 wiki，最后把每次问答和输出重新沉淀回库。

## 当前对库的意义

- 这页是知识库建设的执行模板
- 它应持续随着实践更新，而不是固定不变
- 后续所有新专题和新工作流，都应优先对齐这里的目录、字段和顺序约定
