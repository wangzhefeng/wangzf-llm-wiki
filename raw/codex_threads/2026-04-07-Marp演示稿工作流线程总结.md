# 3. 操作过程摘要

## 阶段一

- 做了什么：查看 `outputs/` 结构、目标结果页内容、本机 `node/npm/brew/Chrome` 环境，并基于官方信息给出 Marp 用法与安装路径。
- 为什么这样做：避免在没有目录上下文和本机前置条件的情况下给泛化建议。
- 结果如何：确认该仓库适合直接采用 `outputs/answers -> outputs/slides -> outputs/figures` 的组织方式，且本机已有运行 Marp 的基本环境。

## 阶段二

- 做了什么：提权执行 `brew install marp-cli`；生成本地 SVG 图；编写 Marp Markdown；导出 HTML 与 PDF。
- 为什么这样做：用户明确要求“使用 brew 安装并生成 slide，且要求本地图片”。
- 结果如何：汇报型 slide 与本地图片链路跑通，PDF 导出成功。

## 阶段三

- 做了什么：新增 Marp 工作流页面，并将其挂接到已有共享工作流与首页入口。
- 为什么这样做：用户目标从“生成一个 slide”转向“提炼 Codex 在项目里的实际工作流”。
- 结果如何：形成可回看的知识库页面，不再依赖线程记忆。

## 阶段四

- 做了什么：把原先单页 Marp 工作流重构为“总览页 + 汇报型页 + 研究型页”。
- 为什么这样做：单一工作流页难以同时承载“短汇报输出”和“研究型沉淀”两种目标。
- 结果如何：工作流结构更清楚，后续更容易固化成模板或 skill 分支。

## 阶段五

- 做了什么：基于同一篇结果页、来源卡和概念页，生成研究型演示稿与新的本地定位图，并导出 HTML/PDF。
- 为什么这样做：仅拆工作流文档还不够，需要一个已跑通的样例来承载“研究型”模式。
- 结果如何：形成了“汇报型 / 研究型”两种已落地样例，具备后续抽象为模板和 skill 的基础。

# 4. 关键决策

- 决策 1：
  - 背景：仓库里还没有现成的 Marp 组织方式。
  - 选择：直接复用 `outputs/answers/` 作为 slide 内容底稿，图片单独放 `outputs/figures/`，导出物放 `outputs/slides/`。
  - 未选方案：把 slide 内容直接写进 `wiki/` 或把图片混入 `slides/` 目录。
  - 原因：更符合现有知识库分层，也更利于后续复用与批量整理。

- 决策 2：
  - 背景：用户要求用本地图片，而仓库里没有现成图片素材。
  - 选择：由 Codex 直接生成本地 SVG 示意图。
  - 未选方案：依赖外链图片、截图网页、临时不用图。
  - 原因：本地 SVG 最稳定，可版本化、可离线、可再次编辑，最适合沉淀为固定做法。

- 决策 3：
  - 背景：Marp PDF 导出第一次在沙箱内失败，失败点是浏览器进程拉起。
  - 选择：使用提权并显式指定 `--browser chrome` 重新导出。
  - 未选方案：只保留 HTML、不验证 PDF、本地手工再试。
  - 原因：这条线程的目标之一就是跑通“本地图片 + PDF 导出”的完整链路，不能停在半成品。

- 决策 4：
  - 背景：工作流文档开始变得混合，既讲一般流程，又想讲不同用途。
  - 选择：拆成总览、汇报型、研究型三页。
  - 未选方案：继续把所有内容堆在同一页。
  - 原因：这更接近后续 skill 设计所需的信息架构，也便于分别沉淀模板、检查清单和提示词。

- 决策 5：
  - 背景：只有流程文档，没有具体研究型实例。
  - 选择：再生成一版研究型样例演示稿。
  - 未选方案：只保留流程说明，不做样例。
  - 原因：如果没有样例，后续难以准确抽取“研究型 slide”的真实结构与命令链路。

# 5. 有效做法

- 哪些提示方式有效：用户先给明确源文件路径和目标目录，Codex 能快速把任务约束落实到具体文件。
- 哪些上下文提供方式有效：先读 `outputs/README.md`、现有 `wiki/indexes/shared/` 页和相关结果页，比直接开始写 slide 更稳。
- 哪些文件组织方式有效：`answers` 做底稿、`figures` 放本地素材、`slides` 放演示稿与导出物，这条分工非常清楚，适合复用。
- 哪些验证方式有效：不仅验证 Markdown 已写出，还实际跑 `marp` 导出 HTML/PDF，并用 `ls -lh`、`file` 确认文件存在与格式正确。
- 哪些沟通方式有效：用户在每一步都把目标从“解释”推进到“安装与生成”再推进到“沉淀流程”，这个递进式明确化让 Codex 可以持续把一次性操作升级为工作流资产。

# 6. 问题与摩擦点

- 哪些地方反复来回：任务边界从“做一个 slide”多次扩展到“沉淀流程”“拆分两类工作流”“补样例”，信息架构需要不断重构。
- 哪些信息缺失导致效率低：研究型 slide 的受众和使用场景未明确，只能按“自用回顾 + 后续研究”默认处理。
- 哪些操作容易误解：Marp 的 PDF 导出并不只是 CLI 转换，还依赖浏览器进程；如果不知道这一点，很容易误以为命令本身有问题。
- 哪些地方本来可以标准化：本地 SVG 图生成、Marp front matter、HTML/PDF 导出命令、汇报型/研究型结构模板，都可以提前固化。
- 其他摩擦点：Codex 内部技能规则偏强，尤其是 `brainstorming` 与直接执行倾向之间存在明显张力；在这种“用户已经明确要直接做”的场景下，会产生过程噪声。

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：
  - 先确认 `outputs/answers/` 是否已有底稿
  - 再检查本机 Marp 与浏览器环境
  - 再决定是否需要生成本地图片
  - 再输出 slide
  - 最后导出 HTML/PDF 并验证

- 适合沉淀为检查清单的点：
  - 是否已有答案页
  - 是否已有图片素材
  - 是否要求本地图片
  - 是否需要 HTML/PDF 双导出
  - PDF 导出是否要 `--allow-local-files --browser chrome`
  - 生成结果是否已回写到 `wiki/indexes/shared/`

- 适合沉淀为模板的内容：
  - Marp front matter 模板
  - 汇报型 slide 结构模板
  - 研究型 slide 结构模板
  - `outputs/figures/<topic>/` 的图片目录约定
  - “从答案页压缩成 slide”的任务提示词

- 适合写进 AGENTS.md 或 skill 的规则：
  - 在本知识库里，演示稿默认基于 `outputs/answers/` 生成，而不是直接基于原始资料
  - 本地图片优先采用 SVG，本地化到 `outputs/figures/`
  - 生成演示稿后默认尝试导出 HTML 与 PDF
  - PDF 导出默认显式使用 `--allow-local-files --browser chrome`
  - 若用户需求转向“沉淀流程”，应优先补 `wiki/indexes/shared/` 页面，而不是只停留在输出文件

- 明显应避免的反模式：
  - 只解释 Marp 用法，不检查仓库目录与本机环境
  - 只写 `.md` 不实际导出
  - 把工作流知识继续埋在聊天记录里，不回写知识库
  - 把“汇报型”和“研究型”混在一页流程里
  - 为了追求抽象，跳过具体样例

# 8. 可复用素材

- 可复用提示词：
  - 请基于某篇 `outputs/answers/` 结果页生成一份 Marp 演示稿，输出到 `outputs/slides/`，并把本地图片放到 `outputs/figures/`，完成后导出 HTML 和 PDF。
  - 请把这份演示稿按汇报型 / 研究型两种用途拆分。
  - 请把本次做法沉淀到 `wiki/indexes/shared/`，站在后续固化 workflow / skill 的角度写。

- 可复用命令：
  - `brew install marp-cli`
  - `marp xxx.md -o xxx.html`
  - `marp --pdf --allow-local-files --browser chrome xxx.md -o xxx.pdf`

- 可复用文件模板：
  - 汇报型 Marp Markdown 模板
  - 研究型 Marp Markdown 模板
  - `wiki/indexes/shared/` 下的工作流页模板

- 可复用目录约定：
  - `outputs/answers/` 作为底稿
  - `outputs/figures/<topic>/` 作为图片目录
  - `outputs/slides/` 作为演示稿与导出目录
  - `wiki/indexes/shared/` 作为共享工作流沉淀目录

# 11. 一句话结论

- 这条线程的价值不在于学会了 Marp，而在于跑通了“答案页 -> 本地图片 -> slide -> HTML/PDF -> 工作流文档”的完整闭环。

- 它还暴露了一个很实际的技术摩擦点：Marp PDF 导出依赖浏览器进程，必须纳入标准命令与排障经验。
- 更重要的是，这条线程把演示稿任务拆成了汇报型与研究型两种模式，为后续 skill 设计提供了天然分叉。
- 如果后续要做 Codex skill，这条线程最适合被抽成“Marp 演示稿工作流 skill + 本地 SVG 辅助模板 + PDF 导出排障规则”三部分。
