# 1. 线程目标

- 初始目标是把当前仓库改造成一个可持续扩展的 Obsidian 知识库，而不是普通笔记目录。
- 后续目标逐步扩展为：

  - 形成 `raw -> wiki -> outputs` 的工作链
  - 为 Codex 使用该知识库提供提示词、健康检查、开发工作流

- 用户希望的交付物不是单一文档，而是一整套“可用知识库 + 可复用工作流素材”。
- 约束前提：
  - 以当前仓库根目录作为 vault
  - 优先保留原始资料，不直接覆盖旧文档
  - 后续希望沉淀为流程和 skill，而不是只完成一次性整理

# 3. 操作过程摘要

## 阶段一

- 做了什么：
  - 按 `practice_steps.md` 建立目录结构
  - 明确 `raw -> wiki -> outputs` 分层
  - 补齐 Obsidian 最小配置
- 为什么这样做：
  - 先把工作域固定下来，后续才适合持续整理和让 Codex 使用
- 结果如何：
  - 形成了可持续扩展的基础结构
  - 后续所有专题纳入都基于这套结构继续展开

## 阶段二

- 做了什么：
  - 将 `operations-research`、`timeseries` 作为历史个人文档资产纳入
  - 先建来源卡，再建索引和概念页
  - 后续又把原目录迁入 `raw/notes/`
  - 将 `wiki/` 从平铺结构重构为“页面类型优先 + 专题分目录”
- 为什么这样做：
  - 初始平铺结构在两个专题出现后开始失去可维护性
  - 本地旧文档需要既保留可追溯性，又避免继续占根目录
- 结果如何：
  - 知识库从空骨架升级为有两个实际专题的可浏览网络
  - 也暴露出：结构设计会随着专题增长而演化，第一次设计通常不够

## 阶段三

# 4. 关键决策

- 决策 1：
  - 背景：项目一开始只是普通仓库，没有明确知识库边界
  - 选择：直接以仓库根目录作为 Obsidian vault 根目录
  - 未选方案：再套一层 `kb/` 子目录
  - 原因：降低路径复杂度，所有知识资产与配置保持同域

- 决策 2：
  - 背景：历史文档 initially 在根目录下，既影响结构，又需要保留
  - 选择：先保留原目录完成首轮映射，后续统一迁入 `raw/notes/`
  - 未选方案：一开始直接强迁移，或一直放根目录
  - 原因：先保证专题可纳入，再做路径归档，风险更小

- 决策 3：
  - 背景：`wiki/` 初始按 `concepts / indexes / sources` 平铺，后续专题增多
  - 选择：改成“页面类型优先 + 专题分目录”
  - 未选方案：继续平铺；或改成专题优先、把概念/索引/来源混在一起
  - 原因：兼顾页面角色清晰度和专题扩展性

- 决策 4：
  - 背景：新来源入库方式多样，反复描述成本高
  - 选择：为专题纳入、网页入库、仓库入库、健康检查分别写 prompt 模板
  - 未选方案：继续每次人工临时描述
  - 原因：重复任务已明显成型，适合模板化

- 决策 5：
  - 背景：图谱里出现大量孤立点
  - 选择：优先隐藏 `raw/`、`prompts/`、`README`、`practice_steps` 等噪声页，而不是强行补链接
  - 未选方案：为所有孤立页补伪链接
  - 原因：图谱应该展示主知识网络，不应为了视觉完整性破坏页面职责

- 决策 6：
  - 背景：scikit-learn 页面和 `tsproj_ml` 仓库进入知识库时，既要快，又要避免直接写百科
  - 选择：先落 `raw`，再建 `wiki/sources`，再回写 `concepts/indexes`
  - 未选方案：直接写概念页或输出页
  - 原因：符合该知识库方法论，也便于后续回溯来源

# 5. 有效做法

- 哪些提示方式有效：
  - 用户先给出明确计划，再要求 “PLEASE IMPLEMENT THIS PLAN” 的模式非常高效
  - “先忽略某目录内容”“本轮只做首轮闭环”“只提供步骤，不执行”等边界说明有效降低误差
  - 要求输出按固定结构组织，有助于 Codex 产出稳定格式

- 哪些上下文提供方式有效：
  - 直接点名当前知识页、来源卡、索引页，比泛泛说“参考知识库”有效得多
  - 给出明确目录和文件约束，比抽象描述更容易让 Codex 持续执行

- 哪些文件组织方式有效：
  - `raw -> wiki/sources -> wiki/indexes -> wiki/concepts -> outputs`
  - `wiki/` 采用“页面类型 + 专题子目录”
  - `raw/notes/` 作为历史个人文档统一入口
  - `raw/assets/attachments/<topic>/...` 统一附件路径

- 哪些验证方式有效：
  - 用 `find`、`rg`、`sed`、`test -f/-d` 做轻量闭环验证
  - 对图谱问题先分析可见层 orphan，再决定是补链接还是隐藏
  - 对 `.obsidian` 配置修改，需要先确认 Obsidian 是否退出

- 哪些沟通方式有效：
  - 长任务中用户频繁追问“执行”时，Codex 按小闭环推进效果好
  - 在每轮收尾时用“做了什么 / 怎么验证 / 剩余风险”非常适合本项目

# 6. 问题与摩擦点

- 哪些地方反复来回：
  - `wiki/` 的组织方式经历了从平铺到专题分目录的重构
  - 图谱配置做过一次，但被 Obsidian 回写覆盖，需要二次修正

- 哪些信息缺失导致效率低：
  - 仓库来源入库时，代码搜索能力不足，首轮只能主要依赖 README
  - 一些任务最初没有明确“只规划 / 直接实施 / 只回答方法”，需要后续澄清

- 哪些操作容易误解：
  - “孤立页”并不一定要连；很多运维页本来就不该进入主图谱
  - 图谱问题不一定是链接问题，也可能是过滤问题
  - `.obsidian/*.json` 的修改如果在 Obsidian 打开时进行，可能被 UI 状态覆盖

- 哪些地方本来可以标准化：
  - 专题纳入流程
  - 网页来源入库流程
  - 仓库来源入库流程
  - 健康检查流程
  - 图谱治理流程
  - “知识库 + Codex 开发”流程
  - 开发结果回流流程

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：
  - 新专题纳入：先计划，再执行，再验证
  - 新来源入库：`raw -> sources -> indexes -> concepts`
  - 外部来源验证后回流 `outputs`
  - 图谱治理：先判定是否该显示，再判定是否该连

- 适合沉淀为检查清单的点：
  - 每次整理后检查 `raw` 是否遗漏、来源卡是否缺失、索引入口是否补齐、概念是否失联、输出是否回流
  - 修改 `.obsidian` 配置前检查 Obsidian 是否已完全退出
  - 判断孤立页时先区分：知识页 / 运维页 / 原始页

- 适合沉淀为模板的内容：
  - `topic-intake-plan`
  - `topic-intake-execute`
  - `web-source-intake`
  - `repo-source-intake`
  - `knowledge-base-health-check`
  - 线程总结模板本身

- 适合写进 AGENTS.md 或 skill 的规则：
  - 本项目中优先按 `raw -> wiki -> outputs` 工作链行动
  - 遇到结构类问题，优先小步验证，不做大范围猜测
  - 先隐藏图谱噪声页，再考虑是否补链接
  - 外部来源优先生成来源卡，不直接跳到概念页
  - 对 Obsidian 配置改动前，先确认应用已退出

- 明显应避免的反模式：
  - 为了图谱好看给不该联网的页面强行补链接
  - 直接把原始来源写成概念总结，跳过来源层
  - 在 Obsidian 打开时修改图谱配置后立即宣称完成
  - 没有固定 prompt/模板却反复做同类任务
