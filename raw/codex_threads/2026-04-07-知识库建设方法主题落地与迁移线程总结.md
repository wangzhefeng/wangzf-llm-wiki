# 3. 操作过程摘要

## 阶段一

- 做了什么：
  - 围绕 `README`、`practice_steps`、Karpathy 原文规划“知识库建设方法”主题。
  - 明确区分来源卡、索引页、概念页。
- 为什么这样做：
  - 先建立承载结构，后续迁移和归纳才有稳定落点。
- 结果如何：
  - shared 主题骨架先搭起来了，知识整理不再依赖单篇原文。

## 阶段二

- 做了什么：
  - 将 `README` 与 `practice_steps` 从根目录文档迁入 `raw/local-notes/knowledge-base/`。
  - 对 Web Clipper 原文补齐 frontmatter 与字段规范。
- 为什么这样做：
  - 用户希望把它们视为原始来源，而不是继续占用根目录主入口角色。
- 结果如何：
  - 形成了更清晰的 `raw 原始层 + wiki 编译层` 分工。

## 阶段三

- 做了什么：
  - 将 `README.md` 与 `欢迎.md` 的首页职责合并，最终保留 `README.md` 作为统一入口。
  - 清理提示词、workspace 与相关页面中的旧引用。
- 为什么这样做：
  - GitHub 与 Obsidian 双场景都需要一个稳定首页，重复入口会持续制造维护成本。
- 结果如何：
  - 入口更统一，但也暴露出删除旧文件前必须做完整清点。

## 阶段四

- 做了什么：
  - 用户指出 `practice_steps.md` 迁移不完整后，先做差异诊断，再补齐漏迁章节，最后删除旧文件。
  - 随后对“诞生设想”文档也做了一轮完整性补齐。
- 为什么这样做：
  - 迁移类任务不能只看“新文件已经存在”，必须对照原始内容确认覆盖率。
- 结果如何：
  - 线程里最有价值的经验之一被明确化：删除旧文件前必须做覆盖率核查。

## 阶段五

- 做了什么：
  - 吸纳两篇新的知识库相关网页文档。
  - 新增 `知识库 Schema 设计`，把主题整理推进到结构约束层。
- 为什么这样做：
  - 用户关心的不只是“知识库内容”，而是 Codex 如何稳定构建和维护这类知识库。
- 结果如何：
  - 这条线程开始具备提炼 repo 级规则、AGENTS 约束和 skill 的价值。

# 4. 关键决策

- 决策 1：
  - 背景：原始方法文档散落在根目录，不适合继续作为正式知识资产承载。
  - 选择：迁入 `raw/local-notes/knowledge-base/`，按原始来源管理。
  - 未选方案：继续保留在根目录，仅在 wiki 中做引用。
  - 原因：更符合 `raw` 层定位，也便于后续由 AI 继续编译进 `wiki`。

- 决策 2：
  - 背景：`README.md`、`欢迎.md`、迁移说明文档之间存在入口重复。
  - 选择：最终用 `README.md` 作为统一首页，删除 `欢迎.md`。
  - 未选方案：保留双首页，或保留 `欢迎.md` 作为 Obsidian 专用首页。
  - 原因：GitHub 与 Obsidian 共用一个入口，维护成本最低。

- 决策 3：
  - 背景：用户要求删除旧文件，但迁移质量不确定。
  - 选择：先诊断旧文档与新文档的内容覆盖，再执行删除。
  - 未选方案：默认认为迁移已完整，直接清理旧文件。
  - 原因：线程中实际出现了漏迁，说明“先删后查”风险很高。

- 决策 4：
  - 背景：最初整理偏内容组织，后来需求逐渐转向 Codex 如何使用并构建知识库。
  - 选择：增加 `Schema 设计` 这类流程页。
  - 未选方案：只停留在主题总览与来源整理层。
  - 原因：只有把规则显性化，后续才可能抽取为 skill 或仓库级约束。

# 5. 有效做法

- 哪些提示方式有效：
  - 用户直接给出“目标 + 结构要求 + 删除/迁移约束”，比泛泛要求“帮我整理一下”有效得多。
  - 在发现问题时用“希望都进行迁移，最后删除该文件”这种明确边界，能显著减少 Codex 自行做不必要取舍。
- 哪些上下文提供方式有效：
  - 直接指出关键原始文档、目标目录和角色定位，例如“作为知识库诞生文档”“作为执行指引”，非常有效。
  - 提前说明两份文档是“同一个想法但成熟度不同”，有利于 Codex 做合并与主次判断。
- 哪些文件组织方式有效：
  - `raw/local-notes/knowledge-base/` 作为原始方法论专题目录有效。
  - `wiki/sources -> wiki/indexes -> wiki/concepts` 三层组织在主题整理中稳定。
- 哪些验证方式有效：
  - 用 `rg` 查残留引用
  - 用 `sed` 或直接通读比对迁移前后正文
  - 用 `git status --short` 检查本轮改动范围
  - 删除前做存在性检查与覆盖率核查
- 哪些沟通方式有效：
  - 用户在关键节点要求“先诊断再删除”，有效抑制了误删风险。
  - Codex 每步都报告“做了什么、验证了什么、还有什么风险”，有助于持续修正方向。

# 6. 问题与摩擦点

- 哪些地方反复来回：
  - `README`、`欢迎.md`、`practice_steps.md` 的角色和去留经历了多轮调整。
  - 主题整理、文档迁移、首页治理和流程固化在同一线程里逐步叠加，任务边界不断扩张。
- 哪些信息缺失导致效率低：
  - 最初没有统一 raw/frontmatter schema，导致 Web Clipper 文档整理需要临时补规范。
  - 删除旧文件前缺少显式“迁移完整性检查”步骤。
- 哪些操作容易误解：
  - “已经迁移”容易被误解成“内容已完整覆盖”，但实际可能只是新文件已创建。
  - “首页”在 GitHub 和 Obsidian 场景下的角色，一开始没有被统一定义。
- 哪些地方本来可以标准化：
  - 原始文档迁移模板
  - 删除旧文件前的核查清单
  - Web Clipper frontmatter 字段规范
  - shared 主题页标准结构
  - 首页/入口调整时的引用清理流程

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：
  - 新主题落地：先来源卡，再索引页，再概念页
  - 原始方法文档整理：先归档进 `raw`，再由 `wiki` 层建立主题入口
  - 删除旧文档：先比对迁移覆盖率，再查引用，再删除，再复查
  - 新网页摄取：先统一 frontmatter，再决定是否生成来源卡和更新索引
- 适合沉淀为检查清单的点：
  - 是否存在旧文件未迁完内容
  - 是否还有旧 wiki 链接、workspace 引用、提示词引用
  - 新文档是否具有统一 frontmatter
  - 主题页之间是否形成闭环互链
- 适合沉淀为模板的内容：
  - raw 原始文档模板
  - Web Clipper metadata 模板
  - 主题总索引模板
  - 阅读地图模板
  - 迁移说明或历史清单模板
- 适合写进 AGENTS.md 或 skill 的规则：
  - 删除或重命名前必须做引用审计与覆盖率审计
  - 知识库任务优先区分 `raw` 与 `wiki` 层职责
  - 对“方法论/流程类内容”要优先产出结构化规则页，而不只是摘要页
  - 文档迁移任务必须显式报告“哪些内容未迁/未明确”
- 明显应避免的反模式：
  - 看到新文件存在就默认迁移已完成
  - 主题页建完就停止，不检查首页、旧入口、workspace、prompts 等外围引用
  - 把“知识整理”和“流程固化”混写在一页里，导致后续难以抽取 skill

# 11. 一句话结论

这条线程的价值，不在于又补了几篇知识库文档，而在于把 Codex 在本项目中处理“主题建设、文档迁移、入口整理、规范补齐”的真实工作方式暴露了出来。最重要的经验是：知识库类任务不能只做内容整理，必须同步处理目录角色、元数据、入口、旧引用和删除策略。线程中最有价值的可复用模式，是“先建结构，再迁原文，再审计覆盖率，再清理旧入口”。如果后续要做 skill，这条线程最适合拆成“主题落地”“迁移核查”“Web Clipper 规范化”“首页/入口清理”四类。
