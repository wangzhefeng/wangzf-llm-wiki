# 3. 操作过程摘要

## 阶段一

- 做了什么：
  - 先读本地原稿、3 份新增 web 文档、阅读地图、schema 页、工作台页、概念页。
  - 把问题拆成“来源层 / 原则层 / 执行层 / 入口层 / 工作台层”。
- 为什么这样做：
  - 用户问的是“如何重构知识库主题”，不是要补内容本身。
  - 先做角色判断，才能避免大改后仍然混层。
- 结果如何：
  - 明确主问题是页面职责重叠，不是资料缺失。

## 阶段二

- 做了什么：
  - 初步建议把本地“诞生设想”看作外部来源之后的内部稿。
  - 用户补充说明：这页本来就是 Karpathy 模式的本地化吸收版，“本来就是一回事”。
- 为什么这样做：
  - 这是重构中最关键的 provenance 判断。
- 结果如何：
  - 重构策略从“重写两份本地稿”改为：
    - 第一份本地稿只收紧定位。
    - 第二份执行稿重点吸收 `LLM Wiki` 的执行结构。
  - 这是本线程最重要的纠偏点。

## 阶段三

- 做了什么：
  - 先改原则稿。
  - 再改执行稿。
  - 再改阅读地图。
  - 再改统一归纳页。
  - 再改总索引。
  - 最后改工作台和 schema 页。
- 为什么这样做：
  - 先固化“上位页面”，再修“入口页面”和“共享工作台”，风险更低。
  - 小步修改便于用户多轮确认。
- 结果如何：
  - 页面分工被逐步收紧，没有发生大范围返工。

## 阶段四

- 做了什么：
  - 用 `rg` 扫描旧的 `shared` 表述、旧入口、健康检查清单引用。
  - 用 `git diff --check` 做格式校验。
- 为什么这样做：
  - 文档重构常见问题不是正文，而是入口没同步、旧叙述残留。
- 结果如何：
  - 修正了工作台和 schema 页中方法入口与 shared/workflow 边界的表述。
  - 未发现格式错误。

# 4. 关键决策

- 决策 1：
  - 背景：是否把“个人知识库诞生设想”视为外部来源之后的次级稿件。
  - 选择：将其定义为 Karpathy 模式的内部 canonical version。
  - 未选方案：把它降级成普通派生草稿。
  - 原因：用户明确说明这页本来就是本地化吸收版，重新拉开会扭曲来源关系。

- 决策 2：
  - 背景：如何吸收 3 份新增 web 文档。
  - 选择：原则稿少动，执行稿重点吸收 `raw/wiki/schema`、`ingest/query/lint`、`index/log`。
  - 未选方案：两份本地稿都大幅重写。
  - 原因：减少混层，保持原则页稳定，把细化结构压到执行层。

- 决策 3：
  - 背景：阅读地图应该强调“阅读顺序”还是“来源谱系”。
  - 选择：两者都写，但明确区分。
  - 未选方案：只保留阅读顺序。
  - 原因：本线程的核心问题之一就是 provenance 不清。

- 决策 4：
  - 背景：`knowledge-base` 主题页和 `shared` 页面如何分工。
  - 选择：`knowledge-base` 负责方法页组，`shared` 负责工作台与跨主题工作流。
  - 未选方案：继续让方法页和工作台边界模糊。
  - 原因：后续若沉淀 skill，边界必须先稳定。

# 5. 有效做法

- 哪些提示方式有效：
  - 用户连续用“执行”推进，强制 Codex 从建议转入落地，减少空转。
  - 用户明确区分“主题内容整理”与“工作流程提炼”，有助于切换总结视角。
- 哪些上下文提供方式有效：
  - 用户直接给出关键文件路径和 3 份新增 web 材料，定位成本低。
  - 用户在关键处补一句“本来就是一回事”，显著减少错误重构。
- 哪些文件组织方式有效：
  - 把原则稿、执行稿、阅读地图、归纳页、总索引、schema、工作台视为一个页面组处理，而不是孤立改单页。
- 哪些验证方式有效：
  - `sed` / `rg` 读局部上下文。
  - `git diff --check` 验证格式。
  - `rg --files` 检查关键入口是否存在。
- 哪些沟通方式有效：
  - 先给“结构判断”，再逐步打补丁。
  - 每次只扩大一层修改范围，便于用户即时确认。

# 6. 问题与摩擦点

- 哪些地方反复来回：
  - “本地原则稿”和“外部来源”的关系一开始判断偏保守，后由用户纠正。
- 哪些信息缺失导致效率低：
  - 开始阶段未明确“内部稿是否就是 canonical 吸收版”，导致第一次建议有偏差。
  - 历史路径里 `shared` 与 `knowledge-base` 的迁移背景未系统说明，只能边扫边修。
- 哪些操作容易误解：
  - “来源顺序”和“阅读顺序”容易被混成一件事。
  - “外部来源”与“内部原则稿”不是对立关系，容易被误判成替代关系。
- 哪些地方本来可以标准化：
  - 文档重构前的 page-role checklist。
  - 文档组重构后的 residual wording audit。
  - 对“canonical internalization vs draft derivative”的先验确认。

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：
  - 先判定页面组角色，再动手改文档。
  - 先确认 provenance，再决定改哪一层。
  - 改完主题页后，必须补入口页和共享工作台。
  - 最后做一次“旧叙述残留 + 关键入口存在性”检查。
- 适合沉淀为检查清单的点：
  - 这页回答什么问题？
  - 它属于原则层、执行层、归纳层还是工作台层？
  - 它的直接上游来源是谁？
  - 它引用的入口页是否存在？
  - 是否仍残留旧目录/旧边界叙述？
- 适合沉淀为模板的内容：
  - “来源谱系 + 使用顺序”双结构模板。
  - 方法页组总索引模板。
  - 文档重构后的 link audit 模板。
- 适合写进 AGENTS.md 或 skill 的规则：
  - 做知识库元结构重构时，先分“来源层 / 原则层 / 执行层 / 入口层 / 工作台层”。
  - 不要默认把内部原则稿当成外部来源的次级草稿，需先确认其 canonical 身份。
  - 重构文档组时，优先小步补丁，不做一次性大改。
  - 完成后必须做 `rg` 残留扫描和 `git diff --check`。
- 明显应避免的反模式：
  - 直接围绕单页内容改写，不先判断整组页面角色。
  - 把 provenance 问题当成内容润色问题。
  - 只改正文，不补入口和工作台。

# 11. 一句话结论

这条线程的价值不在知识库内容本身，而在于暴露了 Codex 处理“文档组重构”时的真实工作模式：先做页面角色判断，再确认来源关系，再按层递进改文档，最后补入口与残留扫描。最关键的经验是，用户一句对 provenance 的纠偏，足以改变整个重构策略。对 skill 沉淀最有价值的不是具体页面内容，而是这套“角色判断 -> 小步补丁 -> 入口收口 -> 健康检查”的序列。线程也说明，文档重构类任务很适合被固化为 checklist 和 skill，因为其主要风险并不在写作，而在结构误判与旧叙述残留。
