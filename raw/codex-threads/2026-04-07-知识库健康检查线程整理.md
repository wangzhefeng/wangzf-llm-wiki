# 3. 操作过程摘要

## 阶段一：按 repo 内提示词执行健康检查

- 做了什么：先读取 `prompts/maintenance/knowledge-base-health-check.md`、`prompts/README.md`、`欢迎.md`、`raw/README.md`、`wiki/README.md`、`outputs/README.md`、`知识库健康检查清单.md`，再扫描 `raw/`、`wiki/`、`outputs/` 的实际内容。
- 为什么这样做：把 repo 内现成 prompt 和说明页当作任务规范，而不是临时发明检查维度。
- 结果如何：形成了较完整的检查结论，识别出结构问题、内容薄弱但可接受的问题，以及检查通过项。

## 阶段二：暴露“只汇报、不落盘”的流程缺口

- 做了什么：第一次只在对话里汇报，没有立刻写入 `outputs/answers/`；用户追问后，补写了 `outputs/answers/2026-04-05-知识库-健康检查.md`。
- 为什么这样做：最初把任务理解成“执行检查并汇报”，没有把“输出结果持久化”当作默认收尾动作。
- 结果如何：暴露出一个很真实的 Codex 工作流问题：即使 repo 已有 `outputs/` 约定，模型仍可能停在“会话答案”层，不会自动完成结果落地。

## 阶段三：把一次遗漏升级成流程修补

- 做了什么：在 `知识库健康检查清单` 和 `欢迎` 中都加入最新检查结果入口；在检查清单里加入“先看上一轮检查结果”“本轮检查结果是否已落地到 `outputs/answers/`”；在 prompt 中加入“开始前先读上轮结果、本轮必须落地、写完后回链”的执行要求。
- 为什么这样做：用户明确提出，下次开始前会先根据检查结果做维护，所以这次不应只补文件，还应把行为约束固化回仓库。
- 结果如何：一次单点修补上升为流程层修补，形成了更适合后续抽象成 skill 的材料。

## 阶段四：澄清 skill、prompt、上下文发现机制

- 做了什么：明确说明本线程实际激活的 skill 只有 `using-superpowers`；解释 `prompts/maintenance/knowledge-base-health-check.md` 的发现来自 IDE 上下文、打开标签页以及实际读取文件与 `prompts/README.md`。
- 为什么这样做：用户在整理 Codex 历史线程，关心的是模型如何决定做法、如何发现上下文，而不是只关心业务结论。
- 结果如何：把“repo prompt 模板”和“Codex skill”区分开，为后续技能设计提供了边界案例。

# 4. 关键决策

- 决策 1：把 repo 内 prompt 当作执行规范，而不是自行组织检查框架；原因：该项目已经把知识库维护方法写进仓库，直接复用更贴近真实工作流。
- 决策 2：区分“结构问题”与“内容薄弱但可接受的问题”；原因：用户明确要求不要把“已登记但未展开”误报成错误，这影响检查结果的可信度。
- 决策 3：在用户指出遗漏后，不只补写输出文件，还同步改 `清单 + 首页 + prompt`；原因：如果只补单次文件，问题会在下次线程里再次出现。
- 决策 4：最近检查结果入口放两处，而不是只放清单页或首页；原因：清单页面向维护动作，首页面向全局导航，两处各有价值。
- 决策 5：把“先读上一轮检查结果”写入流程；原因：用户后续维护是基于检查结果推进，不应每次重新从零散扫描开始。

# 5. 有效做法

- 有效的上下文提供方式：用户直接给出活动文件 `prompts/maintenance/knowledge-base-health-check.md`，并在 IDE context 中暴露 open tabs，这极大缩短了定位成本。
- 有效的执行方式：先读 repo 内 prompt、README、维护清单，再开始扫描目录与页面；这比直接扫文件更稳。
- 有效的检查方式：把机械检查和抽样阅读结合起来。机械检查负责目录、字段、引用；抽样阅读负责判断“内容薄弱但可接受”与“真结构问题”。
- 有效的验证方式：对文档流程改动，用 `rg` 检查关键文案是否出现，用 `git diff` 检查实际改动范围，足够轻量，也足够可靠。
- 有效的沟通方式：当用户指出遗漏时，不争辩“你没要求写文件”，而是承认漏做并补上，再把遗漏上升成流程问题处理。

# 6. 问题与摩擦点

- 最大摩擦点：第一次执行健康检查时只做了会话汇报，没有自动落到 `outputs/answers/`。
- 第二个摩擦点：repo prompt 存在并不自动等于 Codex 会把它当作“必须执行到落地”的工作流；需要显式流程约束。
- 第三个摩擦点：用户后来专门追问“激活了哪些 skills”“怎么知道 prompt 文件存在”，说明模型内部流程对用户仍然不透明。
- 第四个摩擦点：健康检查结果本身可能继续变成“存在但难找”的文件，如果没有回链入口，`outputs` 仍然会沉默堆积。
- 潜在效率损失点：技能系统强调流程，但 repo 实际任务更多依赖本地 prompt 模板；如果两套机制边界不清，后续仍容易混淆。

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：执行 repo 级检查 prompt 时，必须先读 prompt 本体、相关 README、相关清单页，再做扫描。
- 适合沉淀为固定步骤的动作：检查类任务完成后，默认必须执行“写入 `outputs/answers/` + 更新至少一个回链入口 + 明确下一轮维护起点”。
- 适合沉淀为检查清单的点：`outputs` 是否已落地、是否已回链、是否已有“最近结果”入口、下次维护是否以最近结果为起点。
- 适合沉淀为模板的内容：`YYYY-MM-DD-知识库-健康检查.md` 这种输出文件模板，以及“最近检查记录”区块。
- 适合写进 AGENTS.md 或 skill 的规则：当用户显式打开或点名 repo 内 prompt 文件时，先读该文件和同目录 `README`，把它们视为本次任务规范。
- 适合写进 AGENTS.md 或 skill 的规则：对检查/审计/巡检类任务，默认交付物不是会话回复，而是会话回复 + `outputs` 文件。
- 明显应避免的反模式：把“已经回答用户”误当成“已经完成 repo 内交付”；把 repo prompt 和 Codex skill 混为一谈；发现一次流程缺口后只补当前文件，不补流程源头。

- 还没验证的假设：当前“首页 + 健康检查清单”双入口是否足够支撑长期回看，尚未经过多轮使用验证。
- 后续适合单开线程处理的事项：把这次流程提炼成专门 skill；把“检查完成后自动落地 outputs 并回链”的行为进一步模板化或自动化。

# 11. 一句话结论

- 这条线程最有价值的不是完成了一次健康检查，而是暴露了 Codex 容易停在“会话回答”而不是“仓库交付”的真实缺口。
- 用户的追问把问题从“结果内容对不对”推进到了“流程有没有闭环”，这对 skill 设计非常关键。
- 线程证明：repo 内 prompt、README、维护清单已经足以构成一套半结构化工作流，Codex 的任务是尊重并执行到落地。
- 线程还给出了一个明确的固化方向：检查类任务需要内置“读取上轮结果、输出写入 `outputs`、更新回链入口、明确下轮维护起点”的收尾动作。
