# 3. 操作过程摘要

## 阶段一：根因定位

- 做了什么：先读工作流文档与相关页面，全文检索占位词和占位 wikilink。
- 为什么这样做：先区分“内容层问题”与“工具层显示问题”。
- 结果如何：确认无用节点来自仓库文本中的占位链接，不是 Obsidian 异常。

## 阶段二：定向修复

- 做了什么：把占位链接统一改为反引号包裹的示例展示。
- 为什么这样做：保留示例语义，同时避免被识别为链接。
- 结果如何：示例仍可读，但不再作为图谱节点参与连接。

## 阶段三：健康检查与收尾

- 做了什么：跑坏链/未解析链接/frontmatter/概念回链检查，更新检查结果并补日志回链，最后提交推送。
- 为什么这样做：将“诊断-修复-验证-记录-回链”闭环化，避免只在对话里完成。
- 结果如何：检查项通过，产物已落盘，仓库已推送。

# 4. 关键决策

- 决策 1：
  - 背景：图谱噪声不一定是配置问题。
  - 选择：先查内容源头，再考虑图谱配置。
  - 未选方案：直接调整 `.obsidian/graph.json` 规避。
  - 原因：先治根因，避免掩盖问题。

- 决策 2：
  - 背景：用户要求“示例展示而非实际链接”。
  - 选择：使用 ``[[...]]`` 代码样式。
  - 未选方案：纯文本替换或删除示例。
  - 原因：兼顾文档可读性与图谱洁净度。

- 决策 3：
  - 背景：工作区已有大量现存改动。
  - 选择：按用户指令 `push all code` 执行全量提交推送。
  - 未选方案：只提交本轮改动子集。
  - 原因：用户目标是整体推送，不是最小提交范围。

# 5. 有效做法

- 先读取“最近一次健康检查”再执行新一轮检查，避免重复劳动。
- 用脚本批量检查（坏链、未解析链接、frontmatter、概念来源支撑），效率和一致性明显优于人工逐页扫。
- 将健康检查结果与操作日志分层沉淀（`answers` / `logs`），再从索引页回链，保证可追溯。
- 对“误报”与“真实结构问题”做分类处理，减少无效修复。

# 6. 问题与摩擦点

- 自动扫描初期出现误报：`raw/local-notes` 中代码片段的 `[[...]]` 被误识别为 wikilink。
- 正则命令在 `zsh` 下有一次语法错误，说明验证脚本需要更稳健的实现。
- 脏工作区语境下，若用户不明确“提交范围”，容易产生提交策略歧义。

# 7. 对 Codex 工作流的启发

- 适合沉淀为固定步骤的动作：
  1. 读最近健康检查结果
  2. 跑自动扫描（链接、字段、回链）
  3. 分类问题（真问题/误报）
  4. 先修低成本真问题
  5. 更新同日检查结果
  6. 补操作日志并回链

- 适合沉淀为检查清单的点：
  - 占位 `[[...]]` 是否误入 wiki 文档
  - Markdown 路径是否与真实文件一致（含空格与编码）
  - 来源卡字段齐全性
  - 概念页来源支撑最小约束（至少 1 张来源卡）

- 适合写进 skill/规则的内容：
  - “同日健康检查优先更新同名文件，不重复建新文件”
  - “健康检查结束必须落地结果页 + 日志 + 回链”
  - “先分类误报，再修复”

- 明显应避免的反模式：
  - 只在对话里汇报检查结果、不落文件
  - 把图谱噪声直接当成结构损坏，盲目大规模改文档
